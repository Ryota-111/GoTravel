# 旅行計画の共有機能（共有コード）

2026年8月の調査でわかったことをまとめる。
問い合わせ対応と、次に同じ症状が出たときの調査手順のための資料。

---

## 1. 仕組み

Core Data + CloudKit の自動同期は**プライベートDB**を使うため、他人の Apple ID からは見えない。
そのため共有機能だけは**パブリックDBに手動で書き込んでいる**。

| 項目 | 値 |
|---|---|
| データベース | **パブリックDB**（アプリ内で唯一） |
| レコードタイプ | `SharedTravelPlan` |
| レコードID | `shared_<planId>`（例: `shared_9E6658A5-...`） |
| 検索キー | `shareCode`（**QUERYABLE インデックス必須**） |
| 共有コード形式 | `TRAVEL-XXXXXXXX`（英大文字と数字8桁） |

### 主な処理

| 処理 | 場所 |
|---|---|
| 公開 | `CloudKitService.publishSharedTravelPlan(_:)` |
| コード検索 | `CloudKitService.fetchSharedTravelPlan(byShareCode:)` |
| 参加 | `TravelPlanViewModel.joinPlanByShareCode(_:userId:completion:)` |
| 共有停止 | `TravelPlanViewModel.stopSharing(planId:userId:)` |
| 削除 | `CloudKitService.deleteSharedTravelPlan(planId:)` |

### 流れ

```
オーナー: 共有コード発行
  → updateShareCode() が isShared = true・shareCode・ownerId を設定
  → update() の中から publishSharedTravelPlan() でパブリックDBへ保存

参加者: コード入力
  → fetchSharedTravelPlan(byShareCode:) でパブリックDBを検索
  → 見つかったら sharedWith に自分のIDを追加して publish（書き戻し）
  → saveSharedPlanLocally() でローカルにコピーを保存
```

**参加者も書き込む**点に注意。パブリックDBに Create だけでなく **Write 権限**が要る。

## 2. いちばんの落とし穴：CloudKit の環境

**これが2026年8月の調査で、誤った結論を3回出した原因。**

| ビルド | 見る CloudKit 環境 |
|---|---|
| Xcode から実行（Debug） | **Development** |
| TestFlight / App Store（Release） | **Production** |

環境が違うと、**公開は成功しているのに相手からは見つからない**。
ログには「公開成功」と出るので、バグに見えてしまう。

### 実際に起きたこと

- 実機（Release）と シミュレーター（Debug）でテストしていた
- → 実機は Production、シミュレーターは Development に書いていた
- → 当然どちらからも相手のレコードが見えず、「急に共有できなくなった」と見えた
- 実機を Debug ビルドに直したら解決した

### 確認方法

共有のログに環境を出している（`CloudKitService.environmentHint`）。

```
公開開始 env=Production(リリースビルド) planId=... shareCode=TRAVEL-XXXXXXXX isShared=true
公開成功 env=Production(リリースビルド) planId=...
```

Console.app で `subsystem: com.gmail.taismryotasis.Travory` / `category: sharing` を見る。

> `com.apple.developer.icloud-container-environment` エンタイトルメントを入れると
> ビルド種別を無視して環境が固定される。
> **調査用に一時的に入れた場合は必ず消すこと**（消し忘れて上記の混乱を起こした）。

## 3. スキーマ設定（CloudKit Console）

Production 側で以下を確認済み（2026年8月時点で正常）。

### インデックス

`SharedTravelPlan` の `shareCode` に **QUERYABLE** が必要。
これが無いとコード検索が必ず失敗する。

### Security Roles

`SharedTravelPlan` に対して `_icloud` ロールに **Read / Create / Write** が必要。

- Read が無い → 検索しても0件
- Write が無い → 参加時の書き戻しで失敗

> Development で設定を変えたら、**Deploy Schema Changes で Production に反映**しないと本番に効かない。

### Console でレコードを探すときの注意

- Records タブ → Database を **Public** に、Environment を **Production / Development** どちらか選ぶ
- フィルタに値を入れたら **Return を押して確定**する。押さないと `Missing fieldValue in query filter` が出続ける
- `recordName` で検索しようとすると `Field 'recordName' is not marked queryable` になる。`shareCode` か `ownerId` で引く

## 4. 共有を停止すると何が起きるか

問い合わせ対応で毎回聞かれるので明記しておく。

`stopSharing()` は次を行う:

1. `shareCode = nil`、`isShared = false`、`sharedWith = []`
2. パブリックDBの `shared_<planId>` レコードを**削除**

結果:

- **共有コードは変わる**（`generateShareCode()` は毎回ランダム生成。同じコードは戻らない）
- **古いコードは永久に無効**
- **参加済みのメンバーは全員外れる**。作り直したら全員に入り直してもらう必要がある

### 調査上の問題

問い合わせのユーザーが自分で共有を作り直していた場合、**古いコードのレコードはもう存在しない**。
つまり Console で「見つからない」＝「公開が失敗していた証拠」とは言えない。
**再共有しただけでも同じ結果**になり、区別がつかない。

→ **問い合わせでは「現在表示されている共有コード」を聞くこと。**

## 4.5 エラー文言からの切り分け

参加画面（`JoinTravelPlanView`）のエラー文言は原因をかなり絞れる。

| 参加側に出る文言 | 意味 |
|---|---|
| 「共有コードに一致する旅行計画が見つかりませんでした」 | **検索は成功してヒット0件**。レコードが Production に存在しない。**原因はオーナー側**（下記） |
| 「参加できませんでした。通信環境をご確認のうえ…」 | CKError。参加側の通信・iCloud未サインイン・権限エラーなど |
| 「ログインが必要です」 | 参加側がアプリにサインインしていない |

### 「見つかりませんでした」のときの原因（可能性順）

1. **オーナー側の公開が静かに失敗している（本命）**
   - 2.3.1 以前は公開が `try?` で握り潰され、ログも無い
   - コードは公開の成否と**無関係に**画面に表示され、コピーもできる
   - 典型例: **オーナーがiCloud未サインイン**。Core Data はローカルで動くので
     アプリは普段どおりに見えるが、パブリックDBへの書き込みだけが失敗する
   - 「これまで問題なかった」= これまでの共有ユーザーが全員サインイン済みだっただけ
2. **オーナーが共有を作り直していて、相手が古いコードを使っている**（§4参照）
3. **コードの写し間違い** — 文字種に `O`/`0`・`I`/`1` が両方含まれる。
   手入力・口頭伝達だと混同する。`normalizeShareCode` はO↔0を直せない

→ 確認: オーナーの**現在表示中のコード**で Console（Production）を検索。
   **無ければオーナー側の公開失敗が確定**。iCloudサインイン確認 → 共有作り直しで解消。

## 5. 問い合わせ対応の手順

順番が重要。**作り直しを先に案内すると証拠が消える。**

1. **情報をもらう**
   - 現在画面に表示されている共有コード
   - 参加側に出るエラー文言
   - 参加する方が iCloud にサインインしているか
   - すでに共有を作り直したかどうか
2. **CloudKit Console（Production）で確認**
   - `shareCode` でレコードが存在するか
   - `ownerId` と `sharedWith` の中身
3. **その上で作り直しを案内**（回避策として有効。ただしメンバーが外れることを必ず伝える）

参加する方の iCloud サインインは**作り直しより先に確認する**。
未サインインなら何度作り直しても入れない。

## 6. 修正済みの不具合

### 参加者がオーナーと誤判定される（`fc1e140`）

`saveSharedPlanLocally()` は、ローカルコピーの `userId` を**参加者自身のIDに書き換える**
（`NSFetchedResultsController` の絞り込み条件に合わせるため）。
そのため `userId` でオーナー判定すると**参加者がオーナーと判定される**。

誤判定したまま削除すると、パブリックDBの共有レコードごと消えて
**他のメンバーが誰も参加できなくなる**。

```swift
func isOwner(userId: String) -> Bool {
    if let ownerId {
        return ownerId == userId
    }
    // ownerId は共有時に設定される。無いのは一度も共有していないプラン
    return !isShared && self.userId == userId
}
```

### 公開の失敗が誰にも見えなかった（`3096fd4` `362379d` `5567340` `f95cb44`）

呼び出し側が全部 `try?` で握り潰していたため、
公開が失敗しても画面には共有コードが出て、ユーザーには成功に見えていた。
`os.Logger`（Release でも出る）で各段階を記録するようにした。

### 公開に成功するまでコードを表示しないようにした（2.4）

§4.5 の本命原因への対策。2.3.1 まではコード生成と同時に画面に表示・コピー可能で、
公開は投げっぱなしだった。2.4 から:

- `updateShareCode` が async throws になり、**先にパブリックDBへ公開し、
  成功してからローカルを共有状態にする**。失敗時は共有状態にならない
- `ShareTravelPlanView` は公開成功までコードを表示しない（発行中はスピナー）。
  失敗時はアラート表示。`CKError.notAuthenticated`（iCloud未サインイン）は
  専用の文言で設定アプリへのサインインを案内する
- コード文字種から `O`・`I` を除外（`0`・`1` との写し間違い対策）
- 参加側は0件のとき O↔0・I↔1 を置換した候補でも検索する
  （既存コードには O/I が含まれ得るので両方向を試す）
- 共有停止の確認ダイアログに「メンバー全員が外れる」ことを明記した
