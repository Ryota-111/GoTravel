## 1. 予定ごとの時間帯・現地の時刻に合わせる

### 1-1. いただいた声

- 「何ヶ国かを含む旅行で、予定の時間を各現地時間にしたい。予定ごとにタイムゾーンを設定できるようにしてほしい」（2.8）
- 「現地時間と旅程で立てていた時刻を合わせてほしい。旅程の時間が日本時間で登録されていたからか、当日海外で見返すと日本の時刻のままで、頭の中で『今は＋7時間だからこの電車だな』と考えるのが不便だった」（2.8）

### 1-2. 今の作り（2.7〜）と、届いていない理由

- 予定（`ScheduleItem.timeZoneIdentifier`）と予約は、時間帯をすでに持っている。
- ただ、選べるのは **「現地時間」か「日本時間」の2つだけ**。「現地」は旅行の目的地1か所の時間帯（`DestinationTimeZoneService`。目的地の座標から引く）。
  1. **何ヶ国も回る旅行**では、目的地は1か所しか持てない。ロンドンとパリを回る旅行で、パリの予定をパリ時間で入れられない。
  2. **目的地の座標が引けない旅行**（「ヨーロッパ周遊」など広い言葉、地図で選んでいない）では、切り替えが出ず、すべて日本時間で入る。2つ目のご要望はこれと考えられる。
  3. 「現地時間にそろえる」の案内も、目的地の時間帯が分かるときにしか出ない。
  4. 現地に着いてから「日本時間で入っている」と気づいても、直す入口がタイムラインの上の案内だけで、案内を閉じると戻せない。

### 1-3. 方針

**予定の時間帯を、目的地ではなく「その予定の場所」と「その日」から決める。** 現地に着いたときは端末の時計を手がかりに直せるようにする。

#### (a) 時刻の欄の時間帯を、どこでも選べる

「現地時間 / 日本時間」の2択を、次の選択に広げる。

```
時刻  15:00
時間帯 [ パリ（中央ヨーロッパ時間）▼ ]   日本時間では 22:00
          ├ この予定の場所：パリ
          ├ この日の時間帯：パリ
          ├ 旅行の目的地：ロンドン
          ├ 日本時間
          └ ほかの時間帯を探す…（都市名で検索）
```

- 候補は、予定の場所・その日・目的地・日本・最近使った時間帯。重なるものはまとめる（時差が同じなら同じとみなす、今の `showsSameTime` と同じ考え）。
- 「ほかの時間帯を探す」は `TimeZone.knownTimeZoneIdentifiers` を日本語の都市名で検索する。
- 時間帯を変えても**時:分の数字はそのまま**（今の `keepingWallClock` と同じ）。
- 日本と時差のある候補が1つも無い旅行（国内旅行）では、今までどおり何も出さない。

#### (b) 場所を選んだら、その場所の時間帯にする

- 地図で場所を選ぶと、その場所の時間帯（`MKMapItem.timeZone`）が分かる。日本と時差があれば、時刻をその時間帯に切り替え、「パリの時刻で入れます」と一言添える。
- 時刻をもう入れ終えているときは、数字はそのままで時間帯だけ付け替える。

#### (c) 日ごとの時間帯

- 日程の Day ごとに「この日の時間帯」を持つ（例：Day 1〜3 はロンドン、Day 4〜6 はパリ）。
- 新しい予定は、この日の時間帯から入れ始める。
- 決め方：Day の見出しから選ぶ。予定の場所から自動で推し量らず、案内だけ出す（「この日の予定はパリの場所が多いです。この日をパリ時間にしますか？」）。
- 日程の Day の見出しに「パリ時間・日本より8時間遅い」と出す。

#### (d) 現地に着いたら、端末の時計で直せる

2つ目のご要望への答え。**目的地の座標が無くても、端末がいま海外の時計なら案内を出す。**

- 旅行中（今日が旅行の期間内）で、端末の時間帯が日本と違い、日本時間で入った予定がある日に、その日の上に出す。

```
この日の予定は日本時間で入っています
いまいる場所（パリ）の時刻に合わせますか？
[ 数字はそのまま、パリの時刻にする ]   ← 現地の時刻のつもりで入れたとき
[ 同じ時刻のパリの時計に直す ]           ← 日本時間で正しく入れていたとき（15:00 → 8:00）
[ このまま ]
```

- 2つの直し方の違いを、例の時刻を出して見せる（「15:00 → 15:00（パリ）」「15:00 → 8:00（パリ）」）。どちらか分からないと選べないため。
- その日だけ／この旅行の残りの日すべて、を選べる。

#### (e) 時間帯をまとめて変える（あとから直す入口）

- 旅行計画のメニューに「時間帯をまとめて変える」を置く。日の範囲・時間帯・(d) の2つの直し方を選ぶ。
- 案内を閉じたあとでも、ここから直せる。

#### (f) 表示

- 時刻の横の印（今の `zoneLabel`：「現地」「日本」）はそのまま。何ヶ国もあるときは「パリ」「ロンドン」と都市名を出す。
- 予定の詳細では、もう一方の時刻も添える（「15:00 パリ ・ 日本時間 22:00」）。

### 1-4. データの持ち方

| 項目 | 場所 | 中身 |
|---|---|---|
| 予定の時間帯 | `ScheduleItem.timeZoneIdentifier`（今ある） | どの時間帯でも入る（今は目的地か日本だけ入れている） |
| 日の時間帯 | `DaySchedule.timeZoneIdentifier`（**新しく**、任意） | 日程の JSON の中に入る |
| 最近使った時間帯 | 端末の UserDefaults | 同期しない |

- 日程は JSON（`daySchedulesData`）の中なので、**Core Data・共有レコードとも Deploy は要らない。**
- 2.9 以前のアプリ：
  - 予定の時間帯がどこでも、`ScheduleClock` がそのまま読むので、正しい時刻で出る（印は時間帯の名前になる）。
  - 日の時間帯は知らないので、共有した旅行を 2.9 の人が書き換えると、日の時間帯が消えることがある。新しい予定の初期値にしか使わないので、消えても困らない。

### 1-5. 気をつけること

- 時刻の並べ替え：同じ日に時間帯の違う予定があると、「入れた数字の順」と「本当の時刻の順」が食い違う（ロンドン 9:00 とパリ 9:00）。**本当の時刻の順**で並べる。移動日の並びは、実機で見て決める。
- 日付をまたぐ：日本時間で入れた予定を現地の時計に直すと、前の日・次の日になることがある（日本 1:00 → パリ前日 18:00）。直すときに日を移すか、その日のまま残して印を付けるか。**その日のまま残して「前日 18:00」と出す**のを勧める（予定が勝手に別の日へ動くと見失うため）。
- ウィジェット・通知：今は予定の時間帯で読んでいる（`WidgetSnapshot`）。時間帯が増えても同じ作りで足りるか確かめる。

## 2. カレンダーに入れる

### 2-1. いただいた声

「旅行の予定を Google カレンダーに反映させる形で共有したい。他のアプリで日程を組んでいて、照らし合わせたい。過去の旅行の記録は Travory で残したいので、完全に移るつもりはない」（2.9）

### 2-2. 方針

- **iPhone のカレンダー（EventKit）に書き出す。** iPhone に Google アカウントを入れていれば、書き出す先に Google のカレンダーを選べて、Google カレンダーにもそのまま出る。
- Travory が書き出した予定を覚えておき、**旅行計画を直したらカレンダーも直す。** 書き出したまま古くなるのが一番困るため。
- 書き出すのは Travory → カレンダーの片道だけ。カレンダー側で直したものは Travory に戻さない。

### 2-3. 書き出すもの

| Travory | カレンダー |
|---|---|
| 旅行計画 | 終日の予定（出発日〜帰る日）。タイトル「✈️ 沖縄旅行」、メモに目的地 |
| 日程の予定（時刻あり） | 時刻つきの予定。**予定の時間帯で入れる**（`EKEvent.timeZone`。1章と合わせて、海外の予定も正しい時刻で入る）。場所の名前・住所・メモ |
| 予約（飛行機・宿など） | 時刻つきの予定。便名・予約番号をメモに入れる |
| おでかけ・日常の予定 | 日時の予定 |

- 旅行計画ごとに「カレンダーに入れる」を押す（予定の作成時にも聞く）。全部を一度に入れる設定も置く。
- 何を入れるか（日程の予定・予約・旅行の終日の予定）は選べるようにする。

### 2-4. 作り

- 権限：**フルアクセス**（`requestFullAccessToEvents`）を求める。
  - 書き込みだけの権限では、入れた予定をあとから直す・消すことができない（読めないため）。
  - 権限を求める前に、「入れた予定をあとで直すために、カレンダーを読む許可がいります」と説明する画面を出す。
- 書き出す先のカレンダー：初めては「Travory」というカレンダーを作る（iCloud）。Google などのカレンダーを選ぶこともできる。
- 対応表：Travory の項目の ID → `EKEvent.eventIdentifier` を、**端末の中だけ**に持つ（`CalendarExportStore`、Application Support の JSON）。カレンダーの ID は端末ごとに違うので同期しない。
- 直す時機：旅行計画を保存したとき・共有で変更が届いたとき・アプリを開いたとき。差分だけ直す。
- 消す：旅行計画をゴミ箱に入れたら、カレンダーからも消す。「カレンダーから外す」も置く。
- カレンダー側で予定を消されていたら、もう一度入れずに対応表から外す（消したいから消したと考える）。

### 2-5. 権限を使わない書き出し（おまけ）

- 「.ics ファイルで送る」も置く。共有シートで送れて、Google カレンダーの Web から取り込める。権限が要らない。
- こちらは一度きりの書き出しで、あとから直らないことを書き添える。

### 2-6. 無料か Pro か

**無料**を勧める。ご要望に直接こたえる機能で、Travory を使い続けてもらう理由になるため。

## 3. データの書き出し・読み込み

### 3-1. きっかけ

「旅行当日に全部消えた」お問い合わせ（2026年10月）。データは iCloud（Core Data + CloudKit）にしか無く、iCloud 側で失われると戻せない。2.9.1 で端末に控え（読むだけ）と診断を入れた。3.0 では**自分の手で保存しておいて、戻せる**ようにする。

### 3-2. 方針

- 「プロフィール」→「データの書き出し・読み込み」。
- **書き出し**：すべてのデータを1つのファイル（`Travory_2026-10-13.travory`）にして、「ファイル」アプリやメール、AirDrop で保存する。
- **読み込み**：そのファイルを選ぶと、中身を確かめてから（「旅行計画 12件・予定 30件・場所 45件」）取り込む。
- 定期的に書き出すよう案内する：前の書き出しから3か月たったら、プロフィールに一言出す。

### 3-3. ファイルの中身

ファイルは Apple Archive（`AppleArchive`）で1つにまとめたフォルダ。

```
manifest.json   … 形式の版・書き出した日時・アプリの版・件数
data.json       … 旅行計画・予定・訪れた場所・持ち物のひな形・タグ・カテゴリ・アルバム・やること
images/         … 写真（旅行計画のヘッダー・訪れた場所・アルバム・フォトマップ）
```

- 写真を含めるかは書き出すときに選べる（含めると大きくなる。だいたいの大きさを先に出す）。
- データは今のモデル（`TravelPlan` などの Codable）でそのまま書く。**形式の版**を持ち、あとで項目が増えても古いファイルを読めるようにする（知らない項目は読み飛ばす、無い項目は既定値）。

### 3-4. 読み込みの決まり

- **ID で突き合わせる。** 同じ ID がもう端末にあれば、**新しい方を残す**（`updatedAt` で比べる。無ければ端末の方を残す）。
- 端末に無いものは足す。**読み込みで消すことはしない。**
- 持ち主（`userId`）は**今サインインしている人**に付け替える。
- 共有の情報（共有コード・メンバー）は読み込まない。読み込んだ旅行は共有していない状態になる。
  - 他の人の共有レコードを書き換えたり、共有コードを持ち主でない人が引き継いだりしないため。
  - 同じ共有の旅行がまだ端末にあれば、そちらがそのまま残る（上の「同じ ID」の決まり）。
- ゴミ箱に入っている旅行計画は、ゴミ箱に入ったまま戻す。

### 3-5. 気をつけること

- 読み込んだデータは iCloud へ書き出される。iCloud の容量がいっぱいだと保存できないので、2.9.1 の帯と同じく知らせる。
- 2.9.1 の控え（`TravelPlanBackupStore`）はそのまま残す。控えは「iCloud が外れても見られる」、書き出しは「失っても戻せる」で役目が違う。
- 書き出したファイルには予約番号などが入る。書き出すときに「大切な情報が入っています。人に送らないでください」と添える。

### 3-6. 無料か Pro か

**無料**を勧める。データを失わない安心はすべての人に要るもので、有料にすると「消えたのに戻せなかった」が残るため。

## 4. メモ帳を何枚も・自分用か共有か

### 4-1. いただいた声

「リスト内のメモに関して、複数のメモを登録でき、リスト化されるようになると嬉しい。それぞれ個人用か共有するかも選べると便利」（2.9）

### 4-2. 方針

- 2.9 のメモ帳（1枚の文章）を、**メモの一覧**にする。メモごとに題名と本文。
- メモごとに **「みんなで見る」か「自分だけ」** を選ぶ。
  - 共有していない旅行では選択を出さない（全部自分だけと同じ）。
  - 新しいメモの初期値は「みんなで見る」（2.9 と同じ動き）。
- 一覧では、自分だけのメモに鍵の印を付ける。並び替えできる（リストの並び替えと同じ操作）。

### 4-3. データの持ち方

```swift
struct TripMemo: Codable, Identifiable {
    var id: String
    var title: String
    var body: String
    var isPrivate: Bool
    var authorId: String?
    var updatedAt: Date
}
```

| どこ | 何を入れる |
|---|---|
| Core Data `TravelPlanEntity.memosJSON`（**新しく**） | 自分用・共有用の全部 |
| 共有レコード `SharedTravelPlan.memosJSON`（**新しく**） | **共有用だけ**。自分だけのメモは載せない |
| `memoText`（今ある） | 1枚目の共有メモの本文を写して入れ続ける（2.9 以前のアプリのため） |

- 自分だけのメモは、自分の Core Data（プライベートDB）にしか無いので、他の人には見えない。
- 2.9 からの移し替え：`memoText` があれば、題名「メモ」の共有メモ1枚にする。

### 4-4. 共有での突き合わせ

- メモ単位で突き合わせる（前回そろえたときと比べる、`SharedPlanMerge` の三者比較と同じ）。両方が書き換えたら新しい方。
- 共有レコードから来るのは共有メモだけなので、**自分だけのメモは突き合わせの外に置いて、必ず残す。**
- 2.9 以前の人が `memoText` を書き換えたら、1枚目の共有メモに反映する。

### 4-5. リリース前に必要なこと（Deploy）

- `CD_TravelPlanEntity.CD_memosJSON` と `SharedTravelPlan.memosJSON` を Development に作り、Production に Deploy。
- 手順は `設計_旅行のメモ帳.md` の「リリース前に必要なこと」と同じ。

## 5. カテゴリ（カレンダー）と、カテゴリごとの共有

### 5-1. 方針（2026年10月15日に決定）
2.9 までは Travory のカレンダーは1つだけだった。**カテゴリを増やすと、カレンダー自体が増える。**
カテゴリごとに、自分だけで使うか、相手と共有して一緒に編集するかを分けられる
（「自分用」「家族」「友達」のように）。※ 途中で「タグを共有する」形を作ったが、考え違いだったので作り替えた。

- 予定（おでかけ・日常・記念日）は、どれか1つのカテゴリに入る。`Plan.categoryId` が nil なら「自分用」（実体を持たない既定のカテゴリ）。2.9 までの予定とタグはすべて「自分用」に入る
- **タグはカテゴリごとに持つ。** 共有したカテゴリのタグは、メンバー全員で同じものを使う
- **旅行計画はカテゴリに入れない**（今までどおり1件ずつ共有する）。カレンダーには「すべて」と「自分用」で出す
- カレンダータブの上でカテゴリを切り替える（「すべて」「自分用」「家族👥」…「＋」）。カテゴリを選ぶと、そのカテゴリの予定だけを出す
- カレンダータブでタグを選ぶと、選んでいる間はそのタグの予定だけを出す（複数選んだら、どれかが付いていれば出す）
- 予定を作るときは、カレンダーで見ているカテゴリに入れ始める（「すべて」を見ているときは自分用）。作成・編集の画面でカテゴリを選べる（カテゴリを作っている人だけに出る）
- カテゴリを消すと、入っていた予定とタグは「自分用」に移る（消えない）

### 5-2. 共有
- カテゴリの編集画面（カテゴリを長押し、または選んでいるときの右のボタン）の「このカテゴリを共有する」で共有コード（`PLAN-XXXXXXXX`）ができる
- 受け取った人は「共有コードで参加」にコードを入れる。`PLAN-` ならカテゴリ、`TRAVEL-` なら旅行計画として探す
- 共有をやめる（持ち主）・抜ける（メンバー）と、手元ではカテゴリが自分だけのものに戻り、予定とタグは残る
- 繰り返しの予定の次の回は、**カテゴリの持ち主の端末だけが作る**（メンバーごとに作ると人数分に増える）

| みんなで持つ | 自分だけ |
|---|---|
| 題名・日時・終わる時刻・種類・行き先・スケジュール・説明・リンク・繰り返し・色・カテゴリ・タグ | 通知・済みの印・写真 |

### 5-3. データの持ち方

| どこ | 項目 |
|---|---|
| Core Data `PlanCategoryEntity`（新しい） | `id`・`name`・`colorHex`・`order`・`isShared`・`shareCode`・`ownerId`・`sharedWithData`・`createdAt`・`userId` |
| Core Data `PlanEntity` | `categoryId`・`lastEditedBy`・`updatedAt` |
| Core Data `PlanTagEntity` | `categoryId` |
| パブリックDB `SharedCategory`（`sharedcategory_<id>`） | `name`・`colorHex`・`shareCode`・`ownerId`・`sharedWith`・`tagsJSON`・`updatedAt` |
| パブリックDB `SharedPlan`（`sharedplan_<planId>`） | `categoryId`・`tagIDsJSON` と、みんなで持つ項目 |

### 5-4. 作り
- `PlanCategoryManager`（カテゴリの一覧）、`SharedCategoryService`（共有する・やめる・抜ける・参加・同期）
- 突き合わせは `PlanShareMerge`（3方向）。カテゴリのタグも3方向（`SharedCategoryRecord.mergedTags`）。前回そろえた内容は `PlanShareBaseStore`
- 手元にあって相手に無い予定は、**直接取り直して無いと確かめてから**消す（検索に出るのが遅れることがあるため）

### 5-5. 気をつけること
- **相手も 3.0 が要る。** 2.9 以前のアプリに `PLAN-` のコードを入れても見つからない
- Deploy の前にリリースすると、共有を始めたときに保存が失敗する

## 6. 3.0 の Deploy まとめ

**リリースの前に必ず行うこと。** 反映しないまま出すと、メモや予定の共有の保存が Production で失敗する。

| 種類 | 項目 | 使う機能 |
|---|---|---|
| Core Data（プライベートDB） | `CD_TravelPlanEntity.CD_memosJSON`（String） | 4 |
| Core Data（プライベートDB） | 新しいレコードタイプ `CD_PlanCategoryEntity`（項目は 5-3） | 5 |
| Core Data（プライベートDB） | `CD_PlanEntity` の `CD_categoryId`・`CD_lastEditedBy`・`CD_updatedAt`（Date） | 5 |
| Core Data（プライベートDB） | `CD_PlanTagEntity.CD_categoryId` | 5 |
| パブリックDB | `SharedTravelPlan.memosJSON`（String） | 4 |
| パブリックDB | レコードタイプ `SharedCategory`・`SharedPlan`（項目は下） | 5 |
| パブリックDB（索引） | `SharedCategory` の `shareCode`・`ownerId`・`sharedWith`、`SharedPlan` の `categoryId` を **QUERYABLE** | 5 |

`SharedCategory` の項目：`name`・`colorHex`・`shareCode`・`ownerId`・`sharedWith`（文字列のリスト）・`tagsJSON`・`updatedAt`

`SharedPlan` の項目：`categoryId`・`tagIDsJSON`・`title`・`startDate`・`endDate`・`time`・`endTime`・`planType`・`descriptionText`・`linkURL`・`recurrence`・`cardColorHex`・`createdAt`・`updatedAt`・`lastEditedBy`・`placesJSON`・`scheduleItemsJSON`

### 手順
1. **Core Data（プライベートDB）**
   - `CoreDataManager.swift` の `initializesCloudKitSchemaOnLaunch` を true にして、iCloud にサインインした実機でデバッグ実行する
   - CloudKit Console の Development で、上の `CD_` の項目ができたのを確かめる
   - false に戻す
2. **パブリックDB（Development に作る）**：実機のデバッグ実行で次を行う
   - 共有した旅行計画で、「みんなで見る」メモを書いて閉じる（`SharedTravelPlan.memosJSON` ができる）
   - カレンダータブの「＋」でカテゴリを作り、タグを1つ作って、行き先とスケジュールのあるおでかけの予定を入れておく
   - カテゴリの編集画面で「このカテゴリを共有する」（`SharedCategory` と `SharedPlan` の全項目ができる）
3. **索引**：Development の Indexes で、`SharedCategory` の `shareCode`・`ownerId`・`sharedWith`、`SharedPlan` の `categoryId` に QUERYABLE を足す（`recordName` の QUERYABLE も、`SharedTravelPlan` と同じく要るなら足す）
4. **権限**：Security Roles で、`SharedCategory`・`SharedPlan` を `SharedTravelPlan` と同じ設定にする（ログインした人が作成・読み・書き）
5. **Deploy Schema Changes**：上の項目・索引・権限が並んでいることを確かめて、Production に反映する

Core Data のモデルは今の版をそのまま書き換えている（項目を足すだけなので、軽い移行で開ける）。

## 7. 進め方

| 順 | 機能 | 理由 |
|---|---|---|
| 1 | 予定ごとの時間帯 | ご要望が多く、海外旅行中に困っている人がいる。Deploy が要らない |
| 2 | カレンダーに入れる | 1 の時間帯をそのまま使える。Deploy が要らない |
| 3 | 書き出し・読み込み | Deploy が要らない。5 で予定の項目が増える前に形式を決めておく |
| 4 | メモ帳を何枚も | Deploy が要る。小さめ |
| 5 | 予定の共有 | 一番大きい。Deploy が要る |

- 1〜3 だけ先に 2.10 として出し、4・5 を 3.0 にする手もある。1 は旅行の時期に困るので、早く届けたい場合はこちら。
- 機能ごとにブランチを切って、1つずつ実機で確かめてからコミットする。

## 8. 決めてほしいこと

| 問い | 勧め |
|---|---|
| カレンダー・書き出し・予定の共有を無料にするか | 3つとも無料 |
| 書き出しに写真を含められるようにするか | 含められる（選べる） |
| 予定の共有で、済みの印をみんなで持つか | 自分だけ |
| 日本時間で入った予定を現地の時計に直すとき、日をまたいだらどうするか | その日に残して「前日 18:00」と出す |
| 1〜3 を先に出すか、5つまとめて 3.0 にするか | まとめて 3.0（急ぐなら 1〜3 を先に） |
